# Known limitations

This is the full list of the edges I know about; the README keeps a five-item summary of the ones most people meet. Each entry says what the engine does at that edge, what it cannot see, and what you can do about it. Where I could not test something on a real machine, the entry says how I tested it instead.

## Signals and `--stop`

- **Check-then-signal windows.** Every signal follows a check: the launch token for a launched group; at the moment of launch, the kernel's answer that the new group exists (its token may not be open yet), or, for a launch that got no group of its own, its PID answering `kill -0`; for a group run under the library's deadline, the leader answering `kill -0` before TERM and the group still existing before KILL; and `pgrep` for the keep-awake helper. A window of well under a second remains between each check and its signal, in which the checked process could end and the system could reuse its number.
- **Process-table blind spots.** Group membership comes from `pgrep -g`, which can miss a group for a moment around a fork. The engine confirms with the kernel (`kill -0 -- -PGID`) and retries for about a second; if the answer is still unclear, or pgrep fails, the group is reported as "could not be checked", is never signalled, keeps its record, and `--stop` exits 1.
- **An `lsof` that runs but fails** reads as "no process holds the launch token". Nothing is signalled on that reading, because a recorded group is signalled only while a holder of its token is proven, but `--stop` can then delete a token and say everything is down while a process that left its group still runs. With no `lsof` on PATH at all, `--stop` signals nothing; while a recorded group is still running or a launch token is left, it says why and exits 1, and with neither it exits 0 without checking the declared ports for other programs.
- **A launch that gets no process group of its own** (job control off in the shell) is stopped at once by its PID only. Anything it started in that moment shares the engine's own group, is not recorded, and has to be stopped by hand.
- **An interrupt in the instant between a launch and its record.** A service is written to the launch table right after it is proven to lead its own process group, which can take up to about a second. An INT, TERM or HUP in that window leaves it running with no record: `--stop` then names it, while it still holds its launch token, as a process that left its group, and exits 1 without stopping it. Stop it by hand.
- **`--stop` on a stack that never ran here** writes nothing only when the config has no `[compose]` entries. With one, it creates the state folder and a run log, then, once `engine_check` answers, asks compose to stop the services its `[compose]` entries name.
- **A reused group ID.** If the system gives a dead service's recorded group ID to an unrelated program, the engine never signals that program, but it keeps the record: `--stop` exits 1 and names the PIDs until the program ends. To forget the record, delete that entry's line from the launch table, whose path `--print-paths` prints.
- **A lost launch table** (a renamed stack, a different `XDG_STATE_HOME`, or a `--stop` without the `--root` the stack was started with, when its `state_dir` is relative or built on `${STACK_ROOT}`): `--stop` cannot stop what it has no record of. It names a program still holding a declared port, but it cannot prove who started it.
- **A process a job, build, provider, check or heal leaves running** stays in that command's process group, which nothing records once the command ends, so `--stop` neither stops nor sees it, and its closing line, "Everything this stack recorded is down", does not cover it. Start long-running processes as `[service]` entries.
- **A launched process that leaves its group and closes its inherited files** (the launch token among them) cannot be told apart from any other program, so `--stop` cannot find it. If it holds a declared port, `--stop` names it as a program this stack has no record of.
- **An `engine_check` that fails outright** during `--stop` is read as "the container engine is not running"; only a timeout is reported as unchecked.

## Readiness and the end of a run

- **`ready = http URL` without a `port` key** accepts any program that answers the URL. Set `port` to the URL's port as well, so the listener must belong to the launched group. `ready = cmd` proves only what its command checks, and `ready = alive N` only that the process stayed up for N seconds.
- **A service that cannot be checked at the end of the run** (pgrep fails for its group) gets a warning only, so the run can still close with `Open` and exit 0.
- **No watching after the run.** Each service counted ready is checked once more at the end of the run. One that exits after the run is over is not reported: the next run starts it again, and `--stop` lists it as already stopped.

## Plans, paths and config

- **`--plan` and options that are off.** A start stops the entries of an option that is off when that option has `when_off = stop`, including a compose stop for its `[compose]` entries, whether or not they are selected. `--plan` does not show that stop.
- **`--plan` lists an entry whose option is off under "selected"**, and again as off; the entry does not run.
- **`state_dir` and `log_dir` need folders of their own.** stack-up refuses only `/`, HOME, the project root and folders above them. Pointed at a folder that holds other files, it sets `backups/` there to mode 700 on a repair, restarts any `<entry>.log` of the same name on each start, offers every run log there (`run-<time>-<pid>.log`) to `--clean` (with `keep_runs` above 0, so two stacks sharing one `log_dir` see each other's run logs), and `--print-paths` still prints `rm -r` of the whole state folder as the way to forget the stack. The defaults are per stack; keep them, or give each stack new, empty folders.
- **Temporary files during a run.** The here-document check runs once at startup. If bash can no longer write its temporary files later in the run, the here-documents and here-strings the engine still uses read as empty, among them an http probe's URL and expected status (the probe then fails at its deadline), the selection (a `--select` then resolves to nothing and the run closes "Open: nothing was selected"), a failure detail, compose arguments, the preflight problem lists and the `--clean` list. Env provider output is read through a pipe and does not use one.
- **`compose_files` is split on spaces.** Each word is one compose file, resolved against the root, so a project folder with a space in its path works, but a space written inside one file's path splits it into two. `STACK_COMPOSE` is space-separated too, so a job that splits it on spaces gets the wrong files when a path holds a space.
- **Some config errors hide others.** An error in a section header (for example `[service Web]`) or an unknown key stops validation there, so other errors in the file, such as a blank `start`, are reported only on the next run, once it is fixed.
- **`toolchain = nvm`** loads `nvm.sh` only from `$NVM_DIR` (default `~/.nvm`). An nvm installed by a package manager that keeps `nvm.sh` somewhere else is reported as missing. I have not tested a package-manager nvm.

## Platform, install and tests

- **The run lock's `lockf`.** Every start takes a run lock with `lockf -s -t 0 9`, the form current macOS documents, which locks an open file descriptor; so does every `--stop` on a stack that has run here or whose config has a `[compose]` entry, and every `--clean` on a stack that has run here. Older macOS releases may have only the `lockf file command` form; there such a run stops with exit status 1 and says so before it starts or stops anything, and only `--plan`, `--check`, `--help`, `--version` and the `--print-*` modes work, along with a `--stop` on a stack that has never run here and has no `[compose]` entry, or a `--clean` on a stack that has never run here. A start refused this way, or a `--stop` on a stack with a `[compose]` entry, already counts as having run here, because it creates the state folder first, so after one, `--stop` and `--clean` on that stack stop with exit status 1 too. I reasoned that from Apple's published sources and tested it with a stand-in, not on an old release.
- **`uninstall.sh` removes a dangling link** at `PREFIX/bin/stack-up` whose target ends in `/bin/stack-up`, on the reading that it was left by a clone that moved.
- **Interactive prompts** (the option question and the pick menu) are tested through the library's answer seam, not at a real terminal; I have not scripted a real one.
- **Keep-awake is tested with a stand-in.** My tests never touch power state, so the helper they start is a double named `caffeinate`, not `/usr/bin/caffeinate`.
- **The prompt test seam is switched on from the environment.** The shared `lib/` takes answers from `PROMPT_TTY` and `PROMPT_INTERACTIVE` in the environment only when `PROMPT_TEST_SEAM=1` is exported as well, which the tests do. Never export `PROMPT_TEST_SEAM` in a normal shell.
- **The test suite is load-sensitive.** It runs real processes against real deadlines; on a heavily loaded machine it takes several minutes, and its timing margins shrink.
